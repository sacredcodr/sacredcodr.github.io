Vellum

In development

notes updated 20 September 2026

Vellum is a local Windows vault for notes and passwords. It keeps the library on the computer, with no account, server or password-reset service to become part of the trust model.

The project is an exercise in making a small security-sensitive desktop tool understandable. The interface should make the important boundaries visible: what is encrypted, what recovery means, and what an unlocked computer can still expose.

working now

  • Create or open a vault, then search separate password and note entries.
  • Generate passwords and seven-word master passphrases locally.
  • Lock manually or after inactivity, with masked password fields and a timed clipboard clear.
  • Create encrypted backups and an explicitly warned-about recovery copy.

implementation notes

A vault is a file, not an account

Vellum stores the vault locally and opens it with a master passphrase. There is no cloud account, sync service or reset path. That keeps the product small and makes the consequences of losing the passphrase explicit.

The application is built with C++20 and Qt Widgets for Windows x64. The UI is deliberately desktop-shaped: a searchable library on the left, an editor on the right, and lock controls that remain close to the working surface.

Protecting the vault contents

New vaults derive a key with Argon2id and encrypt authenticated payloads with XChaCha20-Poly1305 through libsodium. Entry metadata, including titles and URLs, belongs inside the encrypted payload rather than being left in a readable index.

Each save uses a fresh nonce. The file carries a versioned header and revision information so malformed, altered or unexpectedly old data can be rejected before it is treated as a usable vault.

Backup is different from recovery

An encrypted backup is another copy of the vault and still needs the master passphrase. It is useful against file loss, but it is not a way around forgetting the key.

A recovery copy is deliberately different: it is unencrypted text containing the master passphrase. Vellum warns before creating one and requires it to live in a different folder. Keeping that copy separate is part of the security decision, not an implementation detail.

What the app can and cannot protect

Keys and temporary buffers are cleared where the platform allows it. The app requests clipboard-history exclusion and clears a copied password after ten seconds if clipboard ownership has not changed. Locking also asks Windows to reduce ordinary screen capture.

Those controls are boundaries, not guarantees. Qt widgets can retain plaintext in memory, clipboard managers can copy secrets, crashes can prevent cleanup, and malware or an administrator on an unlocked machine is outside the threat model.

The honest project status

Vellum is early development and has not received an independent security audit. The tests cover authentication, tampering, rollback rejection, recovery, input validation and failure handling. Real suspend and resume behaviour, clipboard edge cases, high-DPI accessibility and fault injection still need verification.

Development packages are marked unsigned. Device sync, browser autofill and passkeys are not currently supported.

things to explore

The next useful work is less about adding a long feature list and more about testing the boundaries: interruption during save, locked-session transitions, accessibility at high DPI, and how clearly the recovery flow communicates its risk.

Building it locally

Vellum currently targets Windows x64 and uses CMake, Qt 6.10.3 and libsodium 1.0.22. The repository contains the build, test and packaging instructions.

Source and current setup notes are available in the GitHub repository.
