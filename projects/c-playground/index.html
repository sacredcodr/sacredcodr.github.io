C playground

early development · notes updated 15 September 2026

A C++ desktop playground for experimenting with small C programs, built around Jonathan Müller's clauf. The aim is to keep the source, diagnostics, and compiler output close together so runtime errors are easier to investigate.

The design and scope are still taking shape. The GitHub repository has a short project introduction; source code and downloads will come later.

reading through clauf

These are the parts of the codebase that connect most directly to the app. Expand a note for the source and the design question it raises.

Inspecting a program doesn't have to run it

In main.cpp, clauf can dump the AST and lauf bytecode before the branch that executes main. Execution is skipped with --compile-only.

That distinction is useful for a playground: inspecting an endless loop should not start it. It gives the interface a reason to separate running code from looking at its compiled form.

The next UI question is how much of a dump to show at once. A raw dump is useful as a reference, but it still leaves the reader to connect it to the source.

There are source locations to build on

The statement visitor in codegen.cpp records a line and column with lauf_asm_build_debug_location. That gives the generated instructions a connection back to the C source.

A small next experiment: make a diagnostic location clickable and select the corresponding line in the editor. First, check what locations survive in the actual error output, including multiline statements and more than one statement on a line.

This doesn't establish that a stepping debugger is ready to wire up. That would need a separate look at lauf's execution APIs.

A VM doesn't settle the isolation question

Clauf's host-function lookup uses dlsym, and its call path uses libffi. The interpreter can interact with native host functions.

The scope is trusted local snippets. Separating the editor from the engine and limiting execution are useful precautions, but they do not make this a sandbox for arbitrary uploaded code.

next experiment

Start with jumping from an error to its source line. Keep the original diagnostic visible so the extra UI can be checked against what clauf actually reported. Syntax highlighting can follow; stepping is still exploratory.

Code observations refer to clauf revision 25b9122. The interface ideas above are directions to explore; this project is not a finished release.
