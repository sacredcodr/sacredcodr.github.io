What a decompiler can actually tell you

reverse engineering

A decompiler can recover a useful description of a function's behaviour without recovering the source that produced it. The distinction becomes clearer with a small example: a function that caps an unsigned value at seven.

Start with something we can check

This example was compiled with Ubuntu Clang 18.1.3 for x86_64-pc-linux-gnu, using -O2. The following is the compiler's emitted Intel-syntax assembly, with directives and comments omitted. It is not a decompiler capture.

Under this target's calling convention, the argument arrives in edi and the result is returned in eax. These register assignments are specific to this example's ABI; don't carry them over to Windows x64 without checking.

Read the operation before naming its purpose

cmp edi, 7 sets flags as though subtracting seven from the input. mov eax, 7 prepares the default result without changing those flags. Then cmovb copies the input into the result if the comparison was unsigned-below. Otherwise, seven stays in eax.

At exactly seven, the move isn't taken, but the result is still seven. That is why this sequence matches the source even though its condition is phrased differently.

This reconstruction explains the instructions. It cannot establish whether the original author used an if, a conditional expression, or an inlined helper. A decompiler's choice of one readable form is not evidence that the author chose the same form. Hex-Rays describes this distinction in Return to the sources?.

One letter changes the interpretation

Now change the parameter and return type to int, leaving the body unchanged. In this build, the optimized instructions are identical except for cmovl in place of cmovb.

cmovb tests the carry flag for unsigned-below. cmovl tests whether the sign and overflow flags differ, the signed-less condition. The preceding cmp itself does not declare a signed type; the condition consuming its flags supplies the distinction here.

The last row is the useful boundary case. On this target, those bits represent 4,294,967,295 as an unsigned 32-bit value and −1 as a signed 32-bit value. A reconstruction that uses a signed comparison for the unsigned function would give the wrong result there.

That gives us evidence for the comparison's semantics. It still doesn't recover the original type spelling: a typedef or an explicit cast could produce the same operation. Check the caller and other uses before treating a decompiler's inferred parameter type as settled.

Optimization changes the shape you see

At -O0, this same compiler stores values in stack slots and emits a conditional jump, jbe. At -O2, the function above has no conditional jump and no stack frame. A conditional move selects the result instead.

An if in decompiled output therefore needn't correspond to a branch instruction. Likewise, stack temporaries in an unoptimized build needn't each represent a separate variable the author named. The compiler's storage decisions and the decompiler's reconstructed variables are two additional layers between the reader and the source.

What would justify a better name?

capUnsignedAtSeven describes the observed operation. limitRetryCount adds a claim about the application's purpose. Nothing in these four instructions establishes that the value counts retries.

To support that name, follow the argument back to its caller: where is it produced, and what uses the returned value? A loop bound, an allocation size, and a displayed setting can all pass through the same arithmetic. Keep the descriptive name until that surrounding behaviour supports a more specific one.

A useful analysis note

Unsigned 32-bit cap at 7. Confirmed from CMP/CMOVB. Meaning of input not established; inspect callers.

The note separates an instruction-level conclusion from the question still open. That makes it easier to revise the name without throwing away what was actually verified.
